# Homelab Active Directory Environment — Samba4 on Ubuntu Server

A self-built Active Directory Domain Controller environment, designed to demonstrate
core Linux system administration, directory services, and automation scripting skills
in a reproducible, documented lab.

## Overview

| | |
|---|---|
| **Domain** | `HOMELAB.LOCAL` |
| **DC hostname** | `lab-server.homelab.local` |
| **DC IP** | `192.168.64.2` |
| **Host OS** | Ubuntu Server 24.04 LTS (ARM64) |
| **Hypervisor** | UTM (QEMU-based), running on Apple Silicon |
| **AD implementation** | Samba 4 (Active Directory Domain Controller mode) |

This lab was built from a blank VM with no configuration management tooling —
every step, including every failure, was done and diagnosed by hand first, then
automated. That order matters: the automation script in this repo exists *because*
the manual process was well understood first, not as a black box copied from a guide.

## Setup summary

1. Provision Ubuntu Server 24.04 ARM64 in UTM
2. Install and provision Samba as an AD DC (`samba-tool domain provision`)
3. Fix DNS resolution chain (see `TROUBLESHOOTING.md` — this was the hardest part)
4. Verify Kerberos authentication (`kinit administrator@HOMELAB.LOCAL`)
5. Build OU structure and manually verify object placement
6. Write and debug an idempotent bulk-user provisioning script
7. Apply a Fine-Grained Password Policy (PSO) to a privileged group and verify enforcement

## Key skills demonstrated

- **Directory services administration** — OU design, security groups, fine-grained
  password policies (PSOs) as a Linux-native alternative to GPO password settings
- **Systems-level DNS diagnosis** — isolating a resolution failure across four
  distinct layers (application server binding, resolver stub, routing domains,
  static host overrides) rather than guessing at a single fix
- **Defensive Bash scripting** — idempotency, structured logging, and diagnosing
  a real `set -e` arithmetic-evaluation bug rather than working around it blindly
- **Security-conscious defaults** — credentials never printed to console, generated
  password file excluded from version control, elevated accounts held to a stricter
  password policy than standard users

## Notes on security choices

- `creds_output.csv` (generated by the provisioning script) is intentionally excluded
  via `.gitignore` — it contains plaintext initial passwords. In a real environment,
  accounts would be provisioned with a forced password reset on first login instead.
- Passwords are never passed as bare CLI arguments in the automation script's normal
  path; where `samba-tool` requires a positional password argument, this is a known
  limitation of the tool itself (visible in shell history / `ps`) and is called out
  explicitly rather than hidden.
